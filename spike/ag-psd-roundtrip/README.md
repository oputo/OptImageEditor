# Spike: ag-psd による PSD 往復テスト

フェーズ 0（T 案の技術検証）の第 1 弾。

- ライブラリ: ag-psd 31.0.2（Node 22）
- 判定役: psd-tools 1.23
- 実施日: 2026-10-05

## 使い方

```bash
npm install
node roundtrip.mjs <a.psd> [b.psd ...]   # 無変更で読み書き → out/<name>.rt.psd
node edit_test.mjs <a.psd>               # テキスト変更 + レイヤー非表示 → out/<name>.edit.psd
python apply_passthrough_patch.py        # 改修: 未知ブロックの保持（npm install の後に 1 回）
python compare.py <orig.psd> out/<name>.rt.psd   # 差分レポート（pip install psd-tools）
```

### 編集テスト（`edit_test.mjs`）

テキスト `<A>` を `<A> edited by ag-psd` に変更し、`Layer 1` を非表示にして書き出した。`invalidateTextLayers: true` を指定。

- psd-tools で読み直すと、テキストの変更と非表示は反映されていた。
- 統合画像は **再生成されない**（ag-psd の仕様）。統合画像だけを見るビューワーでは、古い見た目のまま表示される。
  → アプリ側で、保存時に統合画像を自前で合成して書き込む必要がある。

## 要確認（Photoshop 27.10 での確認をオーナーに依頼）

`_tmp/roundtrip/` に書き出したファイルを PS で開き、次の点を確認する。

1. `*.rt.psd` がエラーなく開け、元のファイルと見た目もレイヤー構成も同じか
2. `test_text_1.rt.psd` のテキストレイヤーを、そのまま編集できるか（フォントが ErasITC-Demi のままか）
3. `test_text_1.edit.psd` を開いたとき、`<A>` の文字が新しい文字列で再描画されるか。警告が出るかどうか

### PS 27.10 での確認結果（2026-10-05、オーナーが確認）

| 確認項目 | 結果 |
|---|---|
| 1. `*.rt.psd` が開け、元と同じか | OK |
| 2. `test_text_1.rt.psd` のテキストをそのまま編集できるか | OK |
| 3. `test_text_1.edit.psd` を開いたとき | 開いた時点で「Some text layers might need to be updated before they can be used for vector based output. Do you want to update these layers now?」という確認が出る。ダイアログの背後では `<A>` が古い描画のまま。`Layer 1` の非表示は反映されている。解像度（168ppi）とフォント（Eras Demi ITC / 60px）は保持されている |

- 3 の確認は、`invalidateTextLayers` を指定したときの想定どおりの挙動（PS に再描画を依頼する印）。

## 改修: 未知データの保持（2026-10-05）

`apply_passthrough_patch.py` で ag-psd 31.0.2 の `dist/psdReader.js` と `dist/psdWriter.js` を書き換える（`npm install` の後に実行する）。

### 原因（ソースを読んで確認した事実）

- `readAdditionalLayerInfo` は、対応する処理を持たないブロックを `skipBytes` で読み飛ばし、どこにも残さない。
- イメージリソースも、対応する処理が無い ID は読み飛ばされる（EXIF / IPTC / 印刷設定など）。
- `CAI ` / `OCIO` / `GenI` を元のバイト列のまま保持する処理はソース中に存在するが、`MOCK_HANDLERS = false` で無効化されている。作者も、元のまま保持する必要性は認識していると思われる（推測）。
- `CAI ` は 4 バイト単位で埋め草（パディング）が入っているが、ag-psd は 2 バイト単位でしか読まない。そのため、そのまま保持すると後続のブロックの位置がずれる。改修では、末尾の 0 埋めも含めて保持するようにした。

### 改修内容

| 対象 | 動作 |
|---|---|
| レイヤー単位と文書全体の付加情報（未対応のキー） | ブロック全体（シグネチャから埋め草まで）を `_rawUnknownInfo` に保持し、書き込み時にそのまま出力する |
| イメージリソース（未対応の ID） | ブロック全体を `imageResources._rawUnknownResources` に保持し、書き込み時にそのまま出力する |

### 結果（psd-tools で照合）

| 項目 | 改修前 | 改修後 |
|---|---|---|
| `CAI ` / `OCIO` / `GenI` | 消える | 保持（中身も一致） |
| EXIF（1058）/ IPTC（1028）/ 印刷設定など | 消える | 保持（中身も一致） |
| サムネイル（1036） | 消える | 消える（テストで生成を無効にしているため。アプリでは生成する） |
| `Patt`（パターン） | 消える | 消える。今回は中身が空のため実害なし。ag-psd の `Patt` 対応は部分的なので、パターンを使う PSD では要検証 |

`_tmp/roundtrip/*.passthrough.psd` に改修後の出力を置いた。PS で開けるかの確認が必要。

| 案 | 内容 | トレードオフ |

### その他の発見

- ag-psd の README には「16bit 非対応」とあるが、v30.0.1 の CHANGELOG に「Fixed handling files with 16bit color format」があり、ソースにも 16 / 32bit 用の画素バッファを作る処理がある。**16bit の読み込みは README の記述より進んでいる可能性がある**（推測）。16bit のサンプルで確認したい。
- `useRawData` オプション（v30〜）を使うと、レイヤーの画素を必要になるまで展開しないでおける。大きな PSD のメモリ対策に使える見込み。
- 透明のある文書では、統合画像の半透明画素の RGB に差が出る（最大 42）。アプリが保存時に統合画像を再生成するので、実害はないと判断。

## 暫定的な評価（推測を含む）

- 単純な構成の PSD なら、ag-psd で十分に往復できる。
- 対策が必要な点:
  1. **未知のブロックを保持すること**: ag-psd を改修し、読めないブロックは元のバイナリのまま保持して書き戻す。これができないと、PS の新しい機能のデータが黙って消える。
  2. **統合画像の再生成**: 保存時にアプリ側で合成した統合画像を書き込む。
  3. **メタデータの保持**: EXIF / IPTC などのイメージリソースを、元のバイナリのまま書き戻す。
- 調整レイヤー、スマートオブジェクト、レイヤー効果を含む PSD での検証はまだ。実案件に近いサンプルが届いたら、同じスクリプトで続けて検証する。
