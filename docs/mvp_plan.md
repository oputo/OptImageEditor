## 0. 棚卸しから読み取れること

| 観点 | 内容 | 設計への影響 |
|---|---|---|
| 作業の性質 | ゼロから描くのではなく、3D レンダー・素材集・ComfyUI 出力を**修正・合成**する作業が中心 | ブラシエンジンの優先度は低い（筆圧 △、ABR ×、混合ブラシ ×）。最難関の一つを避けられる |
| PSD の往復 | 開く・レイヤーを保ったまま編集・PS で開き直せる形で保存、がすべて ◎ | **アプリの成否はここで決まる**。PS の要素で自前対応していないものも、壊さず保存し直す設計が必須 |
| レイヤー機能 | グループ、全描画モード、マスク、クリッピング、調整レイヤー、塗りつぶしレイヤーがすべて ◎ | 合成エンジンは最初から PS 互換の計算式で作る |

| スマートオブジェクト / スマートフィルター | ◎ だが「難しければ後回しで可」 | MVP では「保持・表示・基本操作」までにとどめる |
| テキスト | 横書き ◎、作業の流れにも「テキストや矢印の記入」がある | 横書きテキストと矢印などの注釈は MVP に入れる |
| 自動化 | アクション / バッチ / スクリプトが ○ | 後のフェーズ。ローカル AI エージェントからの操作口（CLI / API）と一緒に設計する |
| PS への不満 | 起動の重さ、AI 連携が課金の仕組みに縛られること | 起動の速さと、ローカル AI（ComfyUI）との密な連携を差別化の軸にする |

## 1. 技術的な前提（重要な発見）

**ag-psd は 16bit/チャンネルに非対応**（README に「Does not support 16 bits per channel」と明記。RGB のみ書き込み可）。

- 2026-10-05 の改訂: 16bit を △ に変更（棚卸しシートのメモ欄に追記）。
- これにより「Tauri + ag-psd」の構成が再び有力になった。
- 16bit の PSD は次のように扱う:
  - 表示: 統合画像だけを自前で読む。16bit の統合画像は、非圧縮または RLE 圧縮のチャンネル別データなので、読み込みの難度は低い（推測）。
  - 編集: 8bit に変換したうえで行う（PS の「イメージ > モード > 8 bit/チャンネル」と同じ扱い）。

PSD の入出力ライブラリの比較（一部推測を含む。フェーズ 0 で検証する）:

| 候補 | 16bit | PS 固有データ（調整レイヤー / スマートオブジェクト / テキスト / レイヤー効果）を保持して保存 | 備考 |
|---|---|---|---|
| ag-psd（TS） | × | ○（構造として保持） | 16bit 対応フォーク（`@dogelyfe/ag-psd-16bit`）はあるが、品質は不明 |
| psd-tools（Python） | ○（読み込み） | ○（構造を解析して書き戻す。往復に強い） | 検証の基準や自動テストの照合役として有用。アプリ本体には重い |
| Magick.NET（C#） | ○ | ×（書き込み時にグループや調整レイヤーなどが失われる見込み） | 単純な画像の入出力専用 |
| **自前の PSD 入出力**（Rust / C# / TS） | ○ | ○（未対応のデータは元のバイナリをそのまま保持して書き戻す） | 仕様は公開されている。ag-psd と psd-tools を参照実装にできる。工数は中〜高 |

→ 8bit が中心なら、まず ag-psd で PS 固有のデータをどこまで保持して往復できるかをフェーズ 0 で検証する。足りない部分だけ自前で補う、という順序にする。調整レイヤーとスマートオブジェクトのデータを ag-psd がどこまで保持するかは未確認（推測では、構造としては読み書きできる）。

## 2. フェーズ計画

### フェーズ 0: 技術検証（1〜2 週間想定）

**進捗（2026-10-05）**

- PSD 入出力: 合格。改修版 ag-psd で、テキスト・調整レイヤー・ベタ塗り・グループ・埋め込みスマートオブジェクトを含む PSD を往復でき、PS 27.10 で開けて編集できることを確認した。詳細は `spike/ag-psd-roundtrip/README.md`。
- 表示性能: Tauri 2 の最小ビューワー（`app/`）で計測した（Windows、WebView2 / Edge 154、GPU の最大テクスチャサイズ 16384）。

  | PSD | サイズ | 合計 | ファイル読み込み | デコード | GPU 転送 | JS ヒープ |
  |---|---|---|---|---|---|---|
  | DSC02987 | 676MB / 5480×5294 | 2.76 秒 | 2.41 秒 | 0.17 秒 | 0.19 秒 | 112MB |
  | AI_IMG_…016 | 602MB / 6810×3744 / 31 レイヤー | 2.98 秒 | 2.15 秒 | 0.65 秒 | 0.17 秒 | 99MB |
  | OPT_LG_L1_4096 | 523MB / 4096² / 55 レイヤー | 2.12 秒 | 1.91 秒 | 0.10 秒 | 0.11 秒 | 65MB |

  - 所要時間の約 8〜9 割はファイル全体の読み込みだった。そこで、統合画像だけを部分的に読む方式（`app/src/psdSlice.ts`）に変更した。再計測はこれから。
- 残り: 部分読み込みでの再計測、全描画モードの合成精度、16bit PSD の表示

目的: 技術構成を確定する。ここで作るものは捨てる前提。

- 対象 PSD: 実案件に近いもの（16bit、グループ、調整レイヤー、スマートオブジェクト、レイヤー効果、テキストを含む）
- 検証すること:
  1. 読み込み → 何も変えずに保存 → PS で開いて差がないか（往復テスト）
  2. 1 レイヤーだけ変更して保存したとき、他の要素が壊れないか
  3. 16bit の PSD を開いたときの挙動（統合画像を表示できるか。8bit に変換して編集できるか）
  4. GPU で合成したとき、全描画モードの結果が PS の統合画像と一致するか（psd-tools で差分を測る）
  5. 8K 画像を開く速度、ズーム・パンの滑らかさ、メモリ使用量
- 判定基準: 往復テスト 100% 合格、合成の誤差がごく小さいこと（具体的な閾値はフェーズ 0 で決める）

## 3. 技術構成の選択肢（フェーズ 0 で確定する）

16bit が必須で、PSD 入出力を自前で持つ可能性が高いことを踏まえた再評価。

| 案 | 構成 | 良い点 | 弱い点 |
|---|---|---|---|
| **R** | Tauri 2 + **Rust の中核**（PSD 入出力・画像処理）+ Web UI（TS）+ WebGPU / WebGL2（RGBA16F）で合成 | 速い。16bit や 32bit も自然に扱える。UI は Web 技術で AI にも書かせやすい。OptPdfEditor（HTML）の資産とつながる | Rust と TS の二つの言語を扱う。Rust と WebView 間の大量の画素の受け渡しが性能上の要所 |
| **C** | **C# .NET 8** + WPF / WinUI 3 + 合成は Direct3D 11 / ComputeSharp など | OptPdfViewer と同じ系統。言語が一つで済む。Windows ネイティブで起動が速い | GPU のキャンバスや UI の作り込みが重い。Windows 専用 |
| **T** | Tauri 2 + TS 中心（ag-psd のフォークを 16bit 対応に改修）+ WebGPU | 最も手早く形になる | 16bit の改修と保守を自分で抱える。巨大な画像では JS 側のメモリが制約になる |

推奨（推測を含む）: **R 案を軸にフェーズ 0 を行う**。PSD 入出力を Rust の独立したライブラリとして作れば、後で UI 側の技術を替えても使い回せる。C 案は、Rust の習得コストを避けたい場合の対抗案。

## 4. フェーズ 0 に入る前に必要なもの

1. 技術構成の方針（R / C / T のどれで検証するか。複数を比べてもよい）
2. 検証用の PSD を 2〜3 本（16bit、グループ、調整レイヤー、スマートオブジェクト、レイヤー効果、テキストを含む、実案件に近いもの）
3. Git リポジトリの初期化と GitHub への登録（`_tmp/` などの検証データを管理対象から外すかどうかを含む）
