# 読み込み経路の性能メモ（2026-10-06）

## 計測（DSC02987.psd、676MB / 統合画像部分 81.6MB、Windows + WebView2）

| 経路 | ディスク読み込み（Rust 側） | WebView に届くまで（read file） | PSD のデコード | 合計 |
|---|---|---|---|---|
| ブラウザの `File.slice()`（HTML5 ドロップ、フェーズ 0） | — | 61 ms | 165 ms | 0.42 秒 |
| Rust `read_range` → IPC（一括） | 13.5〜13.9 ms | 476 ms | 440 ms | 1.09 秒 |
| Rust `read_range` → IPC（8MB に分割して並列） | 2〜8 ms × 11 | 492 ms | 442 ms | 1.09 秒 |
| **Rust → WebView2 SharedBuffer（案 A、実装済み）** | 23〜24 ms | **79 ms** | 455 ms | **0.69 秒** |

## 分かったこと

- 事実: ディスクは約 14ms で読めている。遅いのは **Rust から WebView への受け渡し（IPC）で、約 170MB/秒**。
- 事実: 分割して並列に要求しても速くならない。受け渡しが 1 本の経路で直列に処理されていると推測。
- 事実: Tauri の asset プロトコルは、1 回の Range 応答を最大 1000KB に制限している（`tauri-2.12.1/src/protocol/asset.rs` の `MAX_LEN`）。Tauri 2 の IPC 自体もカスタムスキーム経由なので、カスタムプロトコルに替えても速度は大きく変わらないと推測し、採用を見送った。
- 未解明: IPC 経由にするとデコード時間も 165ms → 440ms に増えた。同じファイルの 3 回目でも同じなので、初回だけの要因ではない。大きなバッファの受け渡しに伴うメモリ処理（GC）の影響を疑っている（推測）。
- 影響: 編集機能ではファイル全体を JS 側に渡す必要がある。600MB を IPC で渡すと、約 3.5 秒かかる計算になる。

## 対策の候補

| 案 | 内容 | 見込み | トレードオフ |
|---|---|---|---|
| A. WebView2 SharedBuffer | Rust が共有メモリに直接ファイルを読み込み、`PostSharedBufferToScript` で JS に渡す（コピーなし） | 受け渡しはほぼディスク速度。編集時のファイル全体の読み込みにも効く | Windows 専用（他の OS では IPC にフォールバック）。COM API を使うため、実装と確認はオーナーの環境でのビルドが前提 |
| B. Rust 側でのデコードと縮小プレビュー | 統合画像を Rust で展開（並列化した RLE 展開）し、画面サイズに縮小した画像を先に送る。原寸は拡大時に送る | 最初の表示は 0.2 秒台の見込み | 表示経路の作り直しが必要。編集時のファイル全体の受け渡しの問題は残る |
| C. 現状維持 | 機能追加を優先し、性能対策は後回しにする | 表示は約 1.1 秒のまま | — |

## 案 A の結果（2026-10-06）

- 共有メモリ方式は Windows で初回からビルドが通り、動作した。受け渡しは 476ms → 79ms（ディスク 24ms + JS 側のコピーなど）。
- デコードは 455ms のままで、IPC が原因ではなかった（前回の推測は外れ）。フェーズ 0 の 165ms との差は未解明。
- 次の候補:
  1. JS 側のデコードが遅くなった原因の調査（Edge ブラウザで `npm run dev` を開いた場合との比較、デコード内訳の計測）
  2. 表示用の統合画像のデコードを Rust に移す（RLE の展開を行単位で並列化し、RGBA を共有メモリに直接書き、JS はコピーせずに GPU へ転送する）
